# Foresight 预测引擎 — 改进与拓展方向建议

> 生成日期：2026-08-14
> 依据材料：`README.md`、`docs/STATUS.md`、`docs/预测Agent-12个月执行规划.md`、`docs/预测Agent-完整实现方案.md`，以及 `src/predictor/`、`scripts/`、`tests/` 源码。
> 本文只回答"从哪些方面入手、先做什么"，不新排预算/路线图（已有 12 个月规划），也不实现任何改动。
> 每个方向统一给四要素：**入口文件 → 服务目标 → 现状 → 可观测起点**。

## 0. 结论先行（优先级总览）

按依赖与收益，建议这样排：

1. **先解 3 个阻塞项**（§1）：ForecastBench 官方 bucket 未配置、类型检查器未配置、`src/predictor/cli.py` 占位。
2. **近期压预测质量与校准**（§2）：服务 M3「难度调整 Brier ≤ 0.11」这个存续关键决策点。
3. **后续做产品化扩展**（§3）：服务 M4–M12 的 B 端 / C 端 / 媒体三线。
4. **贯穿补运维与工程质量**（§4）：成本可观测、数据源可用性、测试下沉。

原则：验证期（M1–M3）零产品化，先过基准评测；产品化方向全部排到 M4 之后。

## 1. 三个已知阻塞项（先做）

以下三项已在 `docs/STATUS.md` 的「阻塞 / 待外部条件」记录，各自有明确解锁条件。

### 1.1 ForecastBench 官方 bucket 未配置（卡 M3 官方战绩）

- **入口**：`src/predictor/data/forecastbench_official.py`、`scripts/fb_submit.py`。
- **现状**：`forecastbench_official.py` 中 6 处 TODO 都与此相关——`QUESTION_SET_RAW_URL` 的 GitHub raw 路径待复核（本机网络把 `raw.githubusercontent.com` 掐断）、`_try_upload_gcs()` 的上传命令/路径待官方回信。`scripts/fb_submit.py` 的「拉题 → 复制进本地题池 → 跑管线 → 生成 forecast set JSON」链路已经就绪，但只有配置了 `FORECASTBENCH_GCS_BUCKET` 且装有 gcloud 时才真正上传，否则只本地落盘 `data/forecast_sets/`。
- **解锁条件**：① 邮件注册 `forecastbench@forecastingresearch.org` 拿官方分配的 GCP bucket 文件夹；② 在 `.env` 配 `FORECASTBENCH_GCS_BUCKET` 并装 gcloud；③ 网络恢复后复核 `QUESTION_SET_RAW_URL` 的 raw 路径格式。
- **可观测起点**：先跑 `python scripts/fb_submit.py --dry-run --limit 20`，确认「拉题 → 预测 → 生成 forecast set」本地链路通，再走真实上传。

### 1.2 类型检查器未配置（卡工程质量）

- **入口**：`pyproject.toml`。
- **现状**：只有 `[tool.ruff]`（lint/format），没有 mypy 或 pyright 配置；而 `docs/预测Agent-完整实现方案.md` 的 Global Constraints 明确要求「ruff + mypy（strict 关、basic 开）」。
- **解锁条件**：在 `pyproject.toml` 加 `[tool.mypy]`（或独立 pyrightconfig），先增量跑（`--follow-imports silent`、只查 `src/predictor/`），再逐步加严，把类型检查纳入常驻门禁。
- **可观测起点**：`uv run mypy src/predictor` 首次跑，按错误清单逐条收敛，不追求一次性全绿。

### 1.3 `src/predictor/cli.py` 是占位（卡 `foresight` 命令）—— ✅ 已解决（2026-08-15，方向纠偏）

- **入口**：`src/predictor/cli.py`、`pyproject.toml`、`scripts/predict_cli.py`、`shell/pi/`。
- **现状**：`foresight` 命令归 pi-fork 的交互 agent（`shell/pi/`，npm link 全局命令）；Python 引擎定位为后端，入口仅 `python -m predictor.cli` 与 `scripts/predict_cli.py`（单行 JSON 契约，供 pi 扩展 pi.exec 调用）。`cli.py` 已承载建题/预测/发布逻辑（predict_once/publish_question），`pyproject.toml` 不再注册 foresight bin。fork 维护与工具扩展见 `shell/BRANDING.md` 与 `.foresight/extensions/foresight-tools.ts`。

## 2. 近期（验证期）——预测质量与校准（服务 M3 Brier ≤ 0.11）

方向按证据强度排序（`README.md` 技术要点：RAG 检索 > 多模型集成取中位数 > 超级预测者提示词 > 极端化 > 市场先验）。

### 2.1 校准层闭环：有零件、无装配

- **入口**：`src/predictor/calibration/isotonic.py`、`src/predictor/calibration/postprocess.py`、`src/predictor/pipeline.py`。
- **现状**：`isotonic.py`（PAVA 的 `fit_isotonic` / `apply`）、`postprocess.py`（`extremize` / `clamp`）、`scoring.py`（`brier` / `log_score`）都已实现且有 `tests/calibration/` 单测；但 `pipeline.py` 只调了 `extremize(prob, alpha=0.2)`，没有「用历史已揭晓题 fit 一个 calibrator → 对新预测 apply」的闭环。
- **可观测起点**：揭晓回填时收集 `(prob, outcome)` 对 → `fit_isotonic` 存库/落盘 → 下一次 `run_prediction` / `websearch_predict` 输出前 `apply`；先在 `tests/calibration/test_isotonic.py` 基础上加一条「fit 后 apply 单调且夹取」的端到端用例。
- **服务目标**：M3 校准调优（实现方案 T13–T16）。

### 2.2 多模型集成：只做「少量异构 + 预算内」的选做项（优先级下调）

- **入口**：`src/predictor/config.py`、`src/predictor/inference/ensemble.py`、`src/predictor/pipeline.py`。
- **现状与判断**：`config.py` 只有 deepseek 单模型，`pipeline.py` 只对同一模型的 n 次采样取中位数。前沿模型高度相关，盲目堆 5–12 个模型边际收益低、API 成本线性涨（会吃掉 M2「单题 <$2.5」预算）；本项目证据排名也把 RAG 检索（+50%）排在集成之前。当前「单模型 × 多采样中位数」已能压掉一部分采样方差，属于够用的基线。
- **可观测起点（选做）**：若做，只加 2–3 个**异构**模型（如推理型 vs 非推理型、不同厂商），`config.py` 加映射 → `ensemble.py` 跨模型中位数；`tests/inference/test_ensemble.py` 的加权中位数已可复用。不做不阻塞 M3。
- **服务目标**：M3 稳健性补强（可选），非主攻方向。

### 2.3 在线模型权重只差「读权重 + 接入集成」（实现方案 T16 差一半）

- **入口**：`src/predictor/data/storage.py`、`src/predictor/inference/ensemble.py`、`src/predictor/pipeline.py`。
- **现状**：Brier EMA 更新已经落地——`storage.py` 的 `resolve_question()` 在揭晓时按 `model_runs` 逐模型 upsert `model_stats`，公式 `brier_ema = (old×9 + new)/10`（即 α=0.1），`tests/data/test_storage.py` 已断言该值；`web/server.py` 的 `/api/system` 也能读到 `model_stats`。缺的是两步接线：① 还没有 `current_weights()`（∝ 1/(brier_ema + 0.01) 归一化）把 `model_stats` 转成权重；② `pipeline.py` 现在 `ensemble(runs)` 不带权重，`ensemble.py` 的 `weights` 参数一直闲置。
- **可观测起点**：新增 `current_weights()` 读 `storage.model_stats()` → 在 `pipeline.py` 里 `ensemble(runs, weights=current_weights())`；先补一条「好模型权重 > 差模型权重」的测试（EMA 落库已有测试，只补读权重这一步）。
- **服务目标**：M3 在线权重 + 长期自动淘汰差模型。

### 2.4 统计基线只覆盖 5 类题，与题族覆盖不匹配

- **入口**：`src/predictor/stats/baselines.py`、`src/predictor/stats/historical.py`、`src/predictor/selection/families.py`。
- **现状**：`baselines.py` 的 `_PATTERNS` 只覆盖 sp500_high / usdcnh_7 / cpi_mom / ffr_meeting / wti_stock；而 `selection/families.py` 出的黄金、布伦特、上证、人民币题基本算不到基线（`scripts/evolve.py` 的 `_build_base_rates` 会对它们 fallback 到「盲档」）。
- **可观测起点**：为黄金/布伦特/上证/人民币各补一个 `baseline_*`（历史滚动频率，复用 `compute_baseline` 的窗口逻辑），加 `tests/stats/` 用例。
- **服务目标**：M3（基准率是校准锚点）+ 题族「难度三档各 ≥25%」纪律（`selection/families.py` 的 `difficulty_tier`）。

### 2.5 回测对比缺「常数基线」对照与可复现化

- **入口**：`src/predictor/eval/backtest.py`、`scripts/compare_backtest.py`、`scripts/backtest.py`。
- **现状**：`eval/backtest.py` 只有 `run_zero_shot_backtest`（零样本基线）；`scripts/compare_backtest.py` 已有「零样本 vs 完整管线」对比框架，但依赖 GDELT 网络窗口，且缺「常数 base rate」这条最简对照。
- **可观测起点**：在 `compare_backtest.py` 加「常数 base rate」基线（用 `stats/baselines.py` 给每个历史题算 base rate），输出三方对比，落盘到脚本已写好的 `data/compare_backtest.json`。
- **服务目标**：M3 里程碑判定依据（`README.md`：Brier ≤ 0.11 才进产品层）。

## 3. 后续（产品化）——Web dashboard 与 B 端 / C 端 / 媒体（服务 M4–M12 三线）

### 3.1 公开榜单缺「投票 / 众包先验回流」（C 端线 M7）

- **入口**：`src/predictor/web/server.py`、`scripts/web_server.py`、`src/predictor/data/storage.py`。
- **现状**：`web/server.py` 的 public 模式只注册 `/api/public/summary` + `/api/public/resolved`；规划 M7「投票功能上线（众包先验数据回流）」未实现。
- **可观测起点**：加 `POST /api/public/vote`（或 `/v1/questions/{id}/vote`），把众包概率写入 storage，后续作为先验注入预测（`pipeline.py` 的 `prior` 参数已预留）。
- **服务目标**：C 端线 M5–M7（榜单 → 投票 → 众包先验资产回流）。

### 3.2 报告只有 Markdown，缺 B 端可交付格式（B 端线 M7 / M11）

- **入口**：`src/predictor/report/generator.py`、`scripts/evolve.py`。
- **现状**：`report/generator.py` 输出纯 Markdown 字符串；`scripts/evolve.py` 的 `write_weekly_review` 只产出 `data/weekly_review/*.md` 骨架。
- **可观测起点**：给 `generate_report` 加 HTML / PDF / 结构化 JSON 导出，或把周报骨架升级为可交付的月度战绩报告。
- **服务目标**：B 端线 M7 月度战绩报告 + M11 年度战绩报告（对外交付）。

### 3.3 人在回路审核流（实现方案 T21）未实现（B 端 POC / C 端可信）

- **入口**：`scripts/predict_cli.py`、`src/predictor/web/server.py`。
- **现状**：`scripts/predict_cli.py` 有 `--publish`（草稿转公开的简单审核门），但方案 T21 的 pending → approved / rejected + audit 日志未实现。
- **可观测起点**：在 `web/server.py` 加 `/api/internal/review` 端点 + predictions 状态字段，或把 `--publish` 扩展为带理由的审核流。
- **服务目标**：B 端 POC（M4–M6）+ C 端「垃圾题不污染战绩」（`README.md` 战绩纪律）。

### 3.4 媒体自动发布缺实现（C 端线 M5 / 媒体桥 M6）

- **入口**：`docs/预测Agent-12个月执行规划.md`（M5 行）、`scripts/`（新增脚本）。
- **现状**：规划 M5「公众号/微博自动发布脚本」未在 `scripts/` 出现；`README.md` 合规红线禁止爬虫/荐股，但主动发布是另一方向，需另立合规边界。
- **可观测起点**：先做只读的「战绩快照 → 发布文案」生成器（复用 `scripts/daily.py` 已产出的 `data/latest_scoreboard.json`），再接第三方发布 API。
- **服务目标**：C 端线 M5 自动发布 + 媒体桥 M6 免费供稿换署名。

## 4. 贯穿——运维 / 工程质量（服务 ops/health + 长期）

### 4.1 单题成本可观测性（M2「单题 < $2.5」目前无法自动核算）

- **入口**：`src/predictor/websearch_predictor.py`、`src/predictor/pipeline.py`、`src/predictor/ops/health.py`。
- **现状**：预测路径不记 token/成本；`ops/health.py` 的检查项只覆盖轮次/积压/锁/行情源/LLM/任务计划器。
- **可观测起点**：在 `add_prediction` / `log_evolution` 记录 model_runs 的 token 用量 → health 面板加「今日成本 / 单题成本」检查。
- **服务目标**：M2 成本纪律 + 预算管控。

### 4.2 数据源可用性分级与降级

- **入口**：`src/predictor/ops/probes.py`、`src/predictor/ops/health.py`、`scripts/daily.py`。
- **现状**：`ops/health.py` 的 `_probe_checks` 只覆盖 quotes / llm / scheduler；GDELT / NewsAPI / CrawlerSource 的失败只在 `scripts/daily.py` 的 `_build_sources` 运行时打印 warning。
- **可观测起点**：probes 加 gdelt / newsapi / crawler 探测，health 面板显示各源可用性。
- **服务目标**：ops 稳定性（`docs/STATUS.md` 的「系统运行正常」）。

### 4.3 补 CLI 编排层冒烟测试（护栏契约测试已覆盖）

- **入口**：`tests/test_websearch_predictor.py`、`tests/data/test_forecastbench_official.py`、`scripts/fb_submit.py`。
- **现状**：测试全绿（今日 `uv run pytest` 283 passed），护栏级契约测试也已存在——`tests/test_websearch_predictor.py` 的 `test_empty_citations_rejected_no_evidence` 覆盖「引用空 → no_evidence 拒绝」，另有非法概率丢弃、缺 web_search_call 丢弃等；`tests/data/test_forecastbench_official.py` 覆盖 fetch 过滤、submit 概率夹取、ledger 去重。真正的缺口是 `scripts/fb_submit.py` 这个 CLI 编排层（`--dry-run`、ledger 去重 → 跑管线 → 生成 forecast set → 记账）没有冒烟测试。
- **可观测起点**：给 `scripts/fb_submit.py` 加一个「fake client + 临时 db + mock question set」的 dry-run 冒烟（断言生成 forecast set JSON 且本地记账），落 `tests/`（如 `tests/test_fb_submit_cli.py`）。
- **服务目标**：工程质量 + 防回归。

## 6. 明确不碰（合规 / 技术裁定，避免走弯路）

- 不碰预测市场 / 博彩、不荐股（`README.md` 合规红线）；Polymarket / Kalshi 只作内部先验。

- 不新增执行计划 / 预算 / 路线图（`docs/预测Agent-12个月执行规划.md` 已覆盖）。
